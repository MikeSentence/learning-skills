# 题型库

六种题型，混搭使用。规则：**不要连续两题同类型**，每题一次只出一个。

---

## 1. 选择题

**用途**：区分易混淆概念、检验"是否真懂"。

**设计要点**：
- 4 个选项，其中 1 个是**最容易踩的坑**（不是随便凑的数）
- 干扰项要"看起来有理"，来自常见误解
- 不要在选项里写"以上都对/都不对"凑数

**示例**：

```
【L2 · 选择题】

Redis 做 MySQL 缓存，更新数据时"先更新数据库，再删除缓存"（Cache-Aside），
相比"先删除缓存，再更新数据库"，主要优势是什么？

A. 保证绝对的强一致性
B. 大幅降低脏数据窗口期（读请求回填旧值的概率更低）
C. 减少了数据库的写压力
D. 避免了缓存穿透
```

正确答案 B。C 是常见误解——删缓存和写数据库的顺序不改变数据库写压力。

---

## 2. 判断题（必须追问为什么）

**用途**：快速定位认知盲区。判断题一定要追问理由，否则只能看出"蒙对"。

**示例**：

```
【L1 · 判断题】

"Kafka 同一个分区内的消息一定是有序的。" —— 对还是错？为什么？
```

> 正确答法：对（单分区内追加写 + 单消费者顺序读）。但要注意"跨分区无序"，以及开启重试时 `max.in.flight.requests.per.connection > 1` 可能乱序——能主动提到这一层算优秀。

---

## 3. 填空题 / 术语题

**用途**：检验能否准确使用术语，而不是"大概知道"。

**示例**：

```
【L3 · 填空】

MySQL 的 update 执行流程中，写 redo log 和写 binlog 的顺序是：
先写 ______（状态为 ______），再写 ______，最后提交事务时把前者改为 ______ 状态。
这个机制叫做 ______。
```

答案：redo log（prepare）→ binlog → redo log 改为 commit；两阶段提交。

---

## 4. 场景题（最高价值）

**用途**：检验能否把知识用到真实工作里。这也是面试最爱问的形式。

**示例**：

```
【L4 · 场景题】

线上出现：用户改了资料，前端立刻查到的还是旧数据，刷新几次才对。
数据库是 MySQL，中间有 Redis 缓存。

你按什么顺序排查？每一步想看什么？
```

> 期望作答：先确认是缓存还是 MD 问题 → 查缓存过期时间 → 看是否"先更新库后删缓存"的并发窗口 → 看是否有读请求在删缓存后回填了旧值 → 结合日志定位。能主动提出"延迟双删"或"订阅 binlog 更新缓存"算优秀。

---

## 5. 反问题（开放式）

**用途**：检验理解深度和举一反三能力。没有标准答案，看推理质量。

**示例**：

```
【L5 · 反问题】

如果这个系统的 QPS 从 1 万涨到 100 万，你刚才那套方案哪一步会最先崩？为什么？
```

> 判定标准：不计对错，看是否指出了具体瓶颈点（连接数、单点、锁竞争、带宽），以及推理链条是否自洽。

---

## 6. 手撕题

**用途**：写代码、推公式、手推算法步骤。

**示例**：

```
【L3 · 手撕】

写一个 Redis + Lua 的令牌桶限流脚本，要求：
1. 原子性
2. 返回是否放行 + 剩余令牌数
3. 说明为什么必须用 Lua 而不是分成两条 Redis 命令
```

> 判卷重点不是代码能否编译，而是：**Lua 的原子性原理讲没讲清**、`KEYS`/`ARGV` 用得对不对、有没有处理 key 不存在的边界。

---

## 出题禁忌

| 不要 | 原因 |
|---|---|
| 一次抛 3 道题 | 用户会挑简单的答，暴露不出问题 |
| 打击式反馈（"这么简单都不会"） | 用户本来就有自我怀疑倾向 |
| 考记忆型偏门细节（某配置项的默认值） | 没价值，还会让用户觉得在钻牛角尖 |
| 同一个考点连出 3 题 | 冗余，应该换角度或升难度 |
| 编造答案 | 底线问题 |
